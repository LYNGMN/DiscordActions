# Google News 원문 URL 변환 요청 보호 설계

## 목적

Google News 원문 URL 변환을 짧은 시간에 많이 요청했을 때 HTTP 429 또는 403이 발생해도 추가 요청을 즉시 멈추고, 다음 실행까지 차단 상태를 보존하며, Discord 알림 자체는 빠뜨리지 않는다.

## 사용자 경험

- 원문 URL 변환이 정상일 때는 지금처럼 언론사 링크를 보낸다.
- 한 실행에서 신규 원문 변환은 메인 기사 최대 5건까지만 시도한다.
- 관련 기사 링크는 기존 성공 캐시 또는 네트워크가 필요 없는 구형 Base64 변환만 사용한다. 새 네트워크 요청이 필요하면 Google News 링크를 그대로 쓴다.
- 요청 예산 소진, 일시적 차단, 변환 실패가 발생해도 기사는 Google News 링크로 전송한다.
- 로그에는 URL과 쿼리 문자열을 남기지 않고 집계 수치와 차단 만료시각만 남긴다.

## 구조

### 실행 단위 요청 예산

`GoogleNewsUrlResolver`는 네트워크가 필요한 메인 기사 변환 시작 횟수를 센다. 기본 한도는 5건이다. 성공 캐시, 구형 Base64 직접 변환, 비활성 설정, 일반 URL 통과는 예산을 소비하지 않는다. 한도를 넘은 기사는 `fallback / budget_exhausted`로 반환한다.

관련 기사에는 `resolve_related()`를 사용한다. 캐시와 구형 직접 변환은 허용하지만 신규 Google 요청은 하지 않고 `fallback / related_network_skipped`로 반환한다. 이 방식은 첫 기사의 관련 링크가 이후 메인 기사 예산을 소진하는 문제를 막는다.

### 영속 회로 차단기

각 워크플로 DB에 `google_news_resolver_state` 테이블을 만든다. 단일 `global` 행에 `blocked_until`, `last_error_code`, `updated_at`을 저장한다.

- HTTP 429: `Retry-After`의 초 또는 HTTP 날짜를 해석한다.
- HTTP 403: 서버가 명시한 `Retry-After`가 있으면 동일하게 사용한다.
- 헤더가 없거나 해석할 수 없으면 1시간을 사용한다.
- 지나치게 짧거나 긴 값은 1분 이상, 6시간 이하로 제한한다.
- 차단 중에는 신규 Google 요청을 전혀 만들지 않고 `fallback / circuit_open`을 반환한다.
- 차단 시간이 지난 뒤 성공한 네트워크 변환은 상태를 지운다.

기사별 기존 실패 백오프 테이블은 그대로 유지한다. 전역 회로 차단은 전체 Google 요청을 멈추고, 기사별 백오프는 같은 실패 기사를 반복 요청하지 않는 서로 다른 역할을 맡는다.

### 안전한 실행 요약

resolver는 다음 집계를 사본으로 제공한다.

- 전체 resolve 호출 수
- 성공 캐시 사용 수
- 구형 직접 변환 수
- 신규 네트워크 변환 시작 수
- 신규 원문 변환 성공 수
- fallback 수
- 예산 초과 수
- 관련 기사 네트워크 생략 수
- 차단 때문에 생략한 수
- 429/403으로 회로를 연 수
- 현재 차단 만료시각

세 스크립트는 실행 종료 시 이 집계만 기록한다. 기사 URL, 응답 전문, RPC 데이터는 기록하지 않는다.

### 예약 분산

세 워크플로의 30분 주기는 유지하되 동시에 시작하지 않도록 UTC 기준으로 분산한다.

- Top: 매시 02분, 32분
- Keyword: 매시 12분, 42분
- Topic: 매시 22분, 52분

각 워크플로는 자기 이름을 concurrency group으로 사용하고 `cancel-in-progress: false`로 설정한다. 예약 실행과 수동 실행이 겹치면 실행 중인 작업을 취소하지 않고 다음 실행 하나만 대기시켜 같은 워크플로의 중복 Google 요청을 막는다.

워크플로 파일 변경은 GitHub에서 비활성 워크플로를 다시 활성화할 수 있으므로 병합 직후 세 워크플로를 다시 비활성화하고 상태를 확인한다. 이번 변경만으로 예약 운영을 켜지는 않는다.

## 오류 처리

- 429/403: 회로 차단 상태를 저장하고 해당 기사와 나머지 기사에 Google News 링크를 사용한다.
- 네트워크/5xx: 기존처럼 2초 후 한 번 재시도하고, 실패하면 기사별 백오프를 저장한다.
- 디코딩 속성 누락 또는 잘못된 RPC 응답: 기사별 백오프를 저장한다. 실행 예산이 상한을 보장하므로 응답 형식 변화가 요청 폭주로 이어지지 않는다.
- DB에 잘못된 차단시각이 있어도 요청을 영구 차단하지 않고 만료된 상태로 취급한다.

## 검증

- 예산을 넘은 신규 기사가 네트워크 요청 없이 fallback 되는지 오프라인 테스트한다.
- 관련 링크가 캐시·구형 변환 외에는 네트워크를 사용하지 않는지 테스트한다.
- `Retry-After` 초/HTTP 날짜, 기본 1시간, 최대 6시간을 테스트한다.
- 새 resolver 인스턴스가 같은 DB의 차단 상태를 재사용하는지 테스트한다.
- 차단 만료 후 성공하면 회로가 정리되는지 테스트한다.
- 통계에 URL이나 응답 데이터가 포함되지 않는지 테스트한다.
- 세 스크립트가 관련 링크 전용 경로와 요약 로그를 사용하는지 테스트한다.
- 세 cron이 정확히 분산됐는지 테스트한다.
- 같은 워크플로의 실행이 겹치지 않도록 concurrency 설정을 테스트한다.
- 전체 unittest, Python 3.8 py_compile, `git diff --check`를 실행한다.
- 실제 Google News 검증은 Discord 전송 없이 신규 기사 최대 3건만 순차 실행하며 부하 테스트는 하지 않는다.

## 범위 밖

- 프록시, 브라우저 자동화, 외부 URL 변환 서비스, 비동기 대량 요청은 추가하지 않는다.
- Discord 메시지 형식, 필터, YouTube 기능, Python 버전은 변경하지 않는다.
- 세 워크플로 사이에 하나의 공유 DB를 새로 만들지 않는다. 차단 상태는 각 기존 DB 안에서 보존한다.
- 병합과 30분 예약 운영 활성화는 구현 게시와 분리된 사용자 승인 단계로 남긴다.
